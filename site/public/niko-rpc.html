Who this is for. You are an AI coding agent (Claude Opus) operating on Niko's server. You have no prior context about the project that requested this — you don't need any. Your whole job is to stand up a NEAR testnet RPC endpoint on this machine and report back the facts listed at the bottom. Treat this page as your complete instructions.

Posture. Be careful and non-destructive. This is someone else's server. Do not remove packages, reconfigure firewalls beyond the one port named here, or touch unrelated services. If a step is ambiguous or a prerequisite is missing, STOP and say so in the report rather than guessing. Nothing here is irreversible if you follow it; keep it that way.

0. Why (one paragraph, so you can make good calls)

The requesting team runs a web app that makes read-only NEAR calls on testnet — mostly query / call_function (contract view methods) and block (chain head). They currently use a third-party hosted RPC that has per-request credit limits and rate limits, which keep running out. A self-hosted testnet RPC on your server removes that cost/limit wall. You are standing up that endpoint. The app will be pointed at it later by the requesting team, not by you — you do not need to touch their app.

Network: testnet only. Not mainnet. All sizing and endpoints below are for testnet.

1. Pick the flavor (your call — report which you chose and why)

There are two ways to serve testnet RPC. Assess this server's real resources (CPU, RAM, free disk, whether Docker is available) and choose the one it can actually sustain. Report which you picked.

Option A — read-only RPC (read-rpc + near-lake) — lightest, preferred if viable

NEAR's read-rpc serves exactly the read methods this app needs (query, call_function, view, block) by reading block data from NEAR's public S3 lake instead of validating the chain itself. No block production, no validation — cheapest to run and keep alive.

  • Rough testnet sizing: ~8 vCPU / 16–32 GB RAM / 500 GB–1 TB NVMe SSD.
  • It needs an S3-reader config pointed at NEAR's public testnet lake bucket (the repo's README has the current bucket + region) and a local datastore (per the repo's deploy docs).
  • Better fit if the server has the disk and you can bring up its datastore cleanly.

Option B — full neard node in --rpc mode — heavier, more robust

A full nearcore neard node configured as a non-validating RPC node: it syncs the testnet chain itself and serves all RPC methods. No S3/lake dependency.

  • Heavier: initial sync takes time and disk; testnet state + recent history is the main cost.
  • Rough testnet sizing: ≥8 vCPU / 32 GB RAM / 1 TB+ NVMe SSD (sync headroom).
  • Use neard init --chain-id testnet, then run with RPC enabled; download a recent testnet snapshot (NEAR publishes these) so you don't sync from genesis.

If the server clearly can't host either comfortably, do not force it — report the constraint (what's missing: disk? RAM? Docker?) and stop. A half-synced or OOM-looping node is worse than none.

2. Requirements for the endpoint (both options must meet these)

Whichever you choose, the finished endpoint MUST satisfy all of these — the requesting app depends on them.

1. Serves testnet reads over HTTP JSON-RPC. It must answer a standard NEAR JSON-RPC POST. Two smoke tests you must run and paste the output of (replace <RPC_URL> with your endpoint):

# (a) chain head — proves liveness
curl -s -X POST <RPC_URL> -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","id":"1","method":"block","params":{"finality":"final"}}' | head -c 400

# (b) a contract view call — proves it serves the reads the app makes
curl -s -X POST <RPC_URL> -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","id":"2","method":"query","params":{
    "request_type":"call_function",
    "finality":"final",
    "account_id":"guest-book.testnet",
    "method_name":"getMessages",
    "args_base64":"e30="}}' | head -c 400

Test (a) must return a block with a recent height. Test (b) must return a result (any SuccessValue is fine — it proves call_function works; guest-book.testnet is a well-known public testnet contract used only as a liveness probe).

2. CORS. The app calls this server-side (not from a browser), so CORS is not strictly required — but if it's trivial to allow * on the RPC path, do. Report whether CORS headers are set.

3. Archival reads (IMPORTANT — report explicitly whether you provide this). The app has a component that reads older transactions via EXPERIMENTAL_tx_status / historical block queries. A normal (non-archival) node returns timeouts / UNKNOWN_BLOCK for aged data. State whether your endpoint serves archival history:

  • Option A (read-rpc) reads from the lake → generally archival-capable; confirm with an old-block query.
  • Option B (neard) is archival only if configured with archive: true (heavier disk). If you run a non-archival neard, say so — the team will keep a separate archival fallback for that one path.

Archival smoke test (query a deliberately old block height, e.g. a few million below head):

curl -s -X POST <ARCHIVAL_RPC_URL> -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","id":"3","method":"block","params":{"block_id":<OLD_HEIGHT>}}' | head -c 300

If it returns the old block → archival works. If UNKNOWN_BLOCK → not archival (report it).

4. Stable URL + port. Expose it on a predictable host:port (or a path behind a reverse proxy). Open only that one port in the firewall if needed. Report the exact <RPC_URL> the team should use.

5. Survives a reboot. Run it under a process supervisor (systemd service or a Docker container with --restart=unless-stopped) so it comes back after a restart. Report the control commands below.

3. Control surface (so the team can operate it without you)

Set it up so these are one-liners, and report the exact commands for THIS server:

  • Is it up? — the health command (the curl smoke test from §2.1, or systemctl status <svc>, or docker ps | grep <name>).
  • Restart / stop / start — the exact commands (systemctl restart <svc> or docker restart <name>).
  • Logs — where they are and how to tail them (journalctl -u <svc> -f or docker logs -f <name>).
  • Sync / health status — for Option B, how to check sync progress (the status method shows sync_info.syncing + latest_block_height). For Option A, how to see it's keeping up with head.
  • Disk watch — which directory holds the data and how to check its size (archival/full nodes grow).

When done — or when you hit a blocker — produce a single markdown report with exactly these fields. This is what the requesting team reads to wire the app and to operate the node. Be precise; paste real command output, not paraphrase.

Why these exact fields

  • The CONTROL — lines are how the team checks it's up and controls it afterward, without you.
  • BLOCKERS / CAVEATS is where you're honest about anything you faked, skipped, or couldn't verify.

5. Hand the report back

Return the filled-in report from §4 as your final message. If anything in §2 couldn't be met, say which and why in BLOCKERS — a partial, honest result is more useful than a confident-but-wrong "it works".
